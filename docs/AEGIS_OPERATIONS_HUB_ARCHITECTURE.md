# Aegis Operations Hub — Product and Integration Architecture

**Decision status:** Approved working direction — **standalone Aegis Operations Hub**.  
**Scope:** Product architecture and build handover only. This document does not itself create a clinical, legal, regulatory, distribution, or treatment recommendation.

## 1. Product boundary

**Aegis is the operations and consent product.** It will be a standalone service that owns governed consent templates, product and material evidence, consent assembly, signatures, immutable records, audit evidence, clinic inventory, procurement workflows, and the future B2B supply experience. It is not a replacement for the specialist clinical applications that conduct a consultation or create a treatment plan.

Dental Telemed, Aesthetics, and MD can remain separate clinical products with their own specialist user experiences. Each calls Aegis when it needs to create, review, sign, retrieve, or audit a consent. This avoids duplicating the safety-critical template, source, signature, and immutable-record services across three applications.

| Product | Primary users | Owns | Does not own |
|---|---|---|---|
| **Aegis Operations Hub** | Clinic administrators, compliance leads, procurement teams, practitioners | Consent template packs, governed sources, procedure/material rules, signed-record archive, audit trail, stock, lots, expiry, procurement, supplier governance, future shop | Diagnosis, treatment recommendation, image interpretation, procedure planning, clinical consultation UX |
| **Dental Telemed** | Dental teams and patients | Dental consultation, dental planning, patient presentation, specialist dental inputs, native consent launch and signing experience | Duplicate consent evidence library or signed-record system |
| **Aesthetics** | Aesthetic clinicians and patients | Aesthetic consultation, facial workflow, treatment planning, injection-map workflow, native consent launch and signing experience | Duplicate product-source governance or stock ledger |
| **MD** | Medical clinicians and patients | General medical consultation and specialty-specific documentation | Duplicate consent template/versioning or audit archive |

> The consent form is **pre-generated by the selected procedure**, then completed by the real products, materials, traceability data, and approved case options selected for that patient. It is not a blank PDF and it is not an AI-generated legal or clinical opinion.

## 2. Consent-builder experience

The clinician works through a short, deliberately controlled sequence. Aegis stores only governed building blocks; the clinical application supplies verified treatment context.

| Step | Clinician action | Aegis action | Required safety boundary |
|---|---|---|---|
| 1. Select module | Choose **Dental**, **Aesthetics**, or **MD** | Filters to the clinic’s enabled template packs and market profiles | A module cannot use a template outside its governance scope. |
| 2. Select procedure | Choose a pre-generated procedure form | Resolves the active procedure template for language and market | Templates are versioned, administrator-controlled, and never silently rewritten after signing. |
| 3. Select products/materials | Choose actual product, implant, graft, membrane, anaesthetic, toxin, filler, device, or lot | Retrieves the approved canonical source and matching disclosure blocks | Unapproved, expired, unsafe, or market-mismatched evidence must block patient-ready assembly. |
| 4. Confirm approved case options | Select configured items such as staged treatment, grafting, sedation, restoration type, or anatomic region | Adds only the matching pre-approved template sections | The clinician confirms choices. Aegis does not interpret imaging or diagnose the patient. |
| 5. Review and sign | Review complete draft with the patient | Captures acknowledgements and signature; seals the exact snapshot, hash, audit event, and PDF | Signed content is append-only. Corrections and withdrawal are separate dated events. |

The existing Aegis implementation already provides most of this engine for aesthetic workflows: clinic templates, governed source records, product and lot selection, anatomy-linked disclosures, acknowledgement capture, patient-held signing links, immutable snapshots, withdrawal events, audit history, supplier governance, inventory traceability, and evidence-freshness review. Dental support extends the same engine with a dental module and controlled procedure/material vocabulary; it should not create a second consent engine.

## 3. Dental and aesthetic template packs

### Aesthetic module

Existing governance supports structured procedures and source-linked risk content for neuromodulators, fillers, biostimulators, polynucleotides, lipolysis products, and other controlled categories. The aesthetic module retains facial-area/injection documentation and product-lot traceability.

### Dental and implant module

The initial dental pack should be limited to high-value, configurable templates rather than attempting to become a complete dental PMS. Each template is a clinic-reviewed starting point that requires jurisdiction and language governance before patient use.

| Initial dental procedure pack | Aegis context selected by clinician | Example governed content categories |
|---|---|---|
| Implant placement | Implant system, reference/part number, implant lot, site/tooth reference, staged/single-stage option | Device/material identity, surgical risks, alternatives, post-operative information |
| Implant restoration / abutment | Implant system, restoration/abutment material, lab reference, maintenance option | Material traceability, maintenance and restoration information |
| Extraction with implant planning | Tooth/site reference, immediate/delayed plan, grafting option | Procedure scope, alternatives, healing and implant-planning disclosures |
| Bone grafting / membrane | Graft and membrane material, lot, source evidence | Material identity, traceability, resorption/healing information |
| Sinus procedure | Site and associated material selections | Procedure-specific reviewed section and follow-up context |
| Sedation / anaesthesia | Clinician-confirmed modality and other approved settings | Separate, locally reviewed consent pack; written consent is required for conscious sedation or general anaesthetic in the Great Britain GDC standard. [1] |
| Post-operative / maintenance | Procedure link, follow-up plan, device/restoration reference | Ongoing care, maintenance, documentation, and patient-contact information |

No template pack should auto-infer nerve distance, bone quality, a diagnostic finding, clinician licensing scope, or a treatment recommendation from imaging, free text, or AI. If a clinical platform later supplies a reviewed measurement, it must be presented as **clinician-confirmed treatment context** and must map only to a pre-approved conditional section. Counsel and clinical leadership control the content of those sections.

## 4. API and data-ownership contract

Aegis should expose a versioned, server-to-server consent API. The clinical applications retain their specialist records and interfaces; Aegis remains the source of truth for consent governance and signed consent artifacts.

| Interaction | Clinical application sends | Aegis returns | Aegis system of record |
|---|---|---|---|
| Create draft | Clinic ID, external patient reference, procedure key, market/language, selected material/product IDs, lot/expiry, clinician-confirmed approved options, idempotency key | Draft ID, template revision, source/disclosure list, current eligibility result | Template resolution and draft assembly |
| Retrieve signing session | Draft/consent ID and patient/session authorization | Minimal patient-facing document payload and one-use signing session | Acknowledgement and signing-session controls |
| Complete signature | Signature method, acknowledgements, signer confirmation, session reference | Sealed consent ID, timestamp, snapshot hash, signed-PDF reference | Immutable signed snapshot, audit chain, withdrawal/notary state |
| Receive lifecycle event | N/A — Aegis sends signed, withdrawn, or evidence-freshness events | Signed record reference and integrity metadata | Audit and event-delivery records |
| Retrieve record | Clinic/user-authorized request, consent ID or external reference | Authorized copy/metadata only | Signed record and current append-only events |

### Identity and tenancy

Every call must be tenant-bound. The originating clinical app authenticates as an approved integration for a clinic, receives only that clinic’s records, and supplies an **external patient reference** rather than assuming that all clinical systems share one patient database. Aegis stores only the patient information legitimately required for its consent function and encrypts sensitive identity fields at rest. The external reference, consent ID, idempotency key, template revision, source version, and signed snapshot hash create a reconciliation trail without requiring the apps to duplicate an entire chart.

### Native signing experience

The patient should see the consent within the originating clinical workflow or a deliberately branded, short-lived Aegis signing session. The clinical product must not rely on a silent background export for a legally significant signature event. Aegis owns the sealed record; the clinical application receives the signed reference and summary after completion.

## 5. Jurisdiction and content governance

The platform must treat jurisdictions as separate evidence and workflow contexts—not as a single “EU compliant” switch.

| Market | Current Aegis position | Required next control |
|---|---|---|
| **Poland / EU** | Poland/EU market profile, Polish/English source governance, registry evidence gates, source audit, and patient-ready eligibility checks are implemented. | Add dental/implant product sources using exact current Polish/EU documents, language, presentation, authorised distribution evidence, and clinic review. Polish medicinal-product information must remain tied to the authorised product information. [2] |
| **Great Britain** | Separate Great Britain profile with MHRA registration, UKCA/CE-transitional route, UK Responsible Person, and evidence-review fields is implemented for devices. | Add dental product evidence per exact presentation. Great Britain rules are not automatically Northern Ireland rules. The GDC requires valid consent, documentation of the discussion, understanding, and written consent for conscious sedation or general anaesthetic. [1] [3] |
| **Malta** | Not yet modelled as a standalone market profile. The existing EU evidence model is a base, not a Malta deployment assertion. | Add a Malta profile, Malta Medicines Authority/economic-operator evidence fields, local template/language selection, and legal-review prompt. Malta’s Medicines Authority describes national registrations/notifications, economic-operator responsibilities, surveillance, and vigilance as part of medical-device oversight. [4] |

The product’s pre-generated template packs are operational starting points, not legal advice or an assurance of malpractice protection. Counsel or an authorised content partner must approve jurisdiction-specific legal language, retention requirements, professional-scope limitations, procedure wording, pricing/financing wording, and mandatory disclosures before any template becomes patient-ready.

## 6. Shop and supply-search boundary

There is **no buyer-facing shop today**. Aegis currently contains the supplier and inventory foundation: controlled product catalogue research, source/evidence governance, supplier due diligence, purchase orders, lot reconciliation, expiry monitoring, supplier incidents, corrective actions, and document quarantine. It does not currently include a customer catalogue, cart, checkout, payments, customer order management, shipping, tax, returns, or marketplace vendor onboarding.

The future supply capability should be phased to prove demand while keeping regulated commerce separate from clinical consent creation.

| Phase | Capability | Explicit boundary |
|---|---|---|
| 1. Governed catalogue and reorder links | Show approved products, stock status, low-stock reminders, authorised supplier reference, and external reorder links | No Aegis payment collection or product sale; supplier/operator controls remain external. |
| 2. Clinic procurement workspace | RFQ/reorder workflow, purchase orders, batch/expiry receipt, stock reconciliation, approval routing | No public marketplace; regulated distribution and tax status remain operator/counsel gates. |
| 3. B2B shop | Verified clinic account, restricted sellable catalogue, cart/order, fulfilment, returns, tax/payment integration, batch traceability | Requires confirmed seller-of-record, distribution licensing, jurisdiction eligibility, payment/tax design, supplier contracts, and counsel approval. |
| 4. Supply search API | Controlled product/evidence/distributor search for Aegis and optionally third-party software | Data licensing, source freshness, source attribution, access control, and commercial terms must be established before external use. |

> A product appearing in a search result, supplier record, or external listing is **not** evidence that it is lawful, clinically suitable, patient-ready, or eligible for sale in a particular market. Those are separate governance decisions.

## 7. Dynamic runtime and portability handover

Git preserves source code and history, but a dynamic healthcare-oriented product also requires a secure runtime, database, object storage, secrets, authentication, background jobs, and monitoring. A temporary sandbox cannot be made permanently available by attaching it; it hibernates and is not a production host. The recoverable handover consists of the GitHub repository, a Git bundle/source archive, the managed-project checkpoint, and the platform Task Data Backup where available.

### Current runtime dependencies

| Dependency | Current role | Portable replacement required for independent operation |
|---|---|---|
| Database | Clinic, template, product, consent, audit, inventory, supplier, and scan metadata | Managed PostgreSQL or equivalent, migrated with integrity checks |
| Object storage | Signatures, PDFs, clinical photos, supplier evidence, and supporting documents | Private S3-compatible storage/MinIO with encrypted access and signed download controls |
| Authentication | Clinic workspace sign-in and role checks | OIDC-compatible authentication with clinic/role claims |
| Secrets | Session signing, storage, integrations, scan/email adapters | Managed server-side secret store; never Git or browser bundle |
| Scheduled work | Evidence freshness, expiry scans, escalation and scan follow-up | Durable scheduler/queue with idempotency and audit logging |
| API/runtime | tRPC/Express integration endpoint and signing workflow | Long-lived Node deployment with TLS, monitoring, backups, and incident ownership |

### Local development recovery

After cloning the repository, a developer can restore dependencies and run the validation suite with:

```bash
pnpm install --frozen-lockfile
pnpm test -- --run
pnpm exec tsc --noEmit
pnpm dev
```

Running the complete application still requires non-committed environment configuration such as database, authentication/session, storage, and integration secrets. Never commit those values. The portable migration plan in `reports/DEMANUS_MIGRATION_PLAN.md` sets out the required data, object, hash, job, and cutover verification before a live independent deployment.
